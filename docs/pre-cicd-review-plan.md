# CI/CD 前のコードレビューと改善計画

作成日: 2026-11-14。対象: 現在の作業ツリー（未コミットの Shelly 対応を含む）。状態: レビュー後、ユーザーの指示で下記の優先修正を実装・検証。指摘の根拠は修正前の作業ツリーに対するもの。CI/CD 配備は検証後に実施する。

## 推奨方針

人感イベントとバッテリーの機能検証に加えて、DB 障害と MQTT の部分受信に対する修正を本格反映の条件にする。Go と依存ライブラリーも更新する。責務の整理はこの修正に必要な範囲から進める。

Rust 言語・コンパイラーは別途評価する。現行アプリは Go 製で、Rust のソース、Cargo の定義、Rust 依存は見つからなかった。Rust コンパイラーの更新だけで現行アプリの処理は変わらない。候補となるデコード処理を測定し、導入効果を判断する。

## 調査範囲と実施済み検査

各 collector、API、共有パッケージ、DB スキーマ・マイグレーション、Web、Compose、Dockerfile、GitHub Actions、運用文書を横断的に確認した。特に Cisco → BTHome → DB → API → Grafana と、障害時の保存・再接続を重点的に読んだ。全機能の障害条件を実機で網羅したという意味ではない。

診断は nms4 の `/tmp/home-metrics-review-20261114` に作成した隔離コピーと Go 1.26.4 コンテナーで実施した。稼働サービスの停止・差し替えは行っていない。

| 検査 | 結果と限界 |
| --- | --- |
| `go vet ./...` | 成功 |
| `go test -race -cover ./...` | 全パッケージ成功。実行した経路で race を検出しなかった。DB 実機結合・全障害条件の保証ではない |
| MQTT 部分受信の再現テスト | タイムアウト後、残りを新しいヘッダーとして読むことを再現。再現用テストは隔離コピーにのみ配置 |
| `govulncheck@v1.9.0 -json ./...` | 関数への呼び出し経路を含む既知の脆弱性22件。静的解析の報告であり、22件すべてが実環境で悪用可能と確認したわけではない |

API のカバレッジは12.4%、Cisco collector は51.7%。数値自体を目標にせず、今回見つかった障害経路と DB/API の契約を重点的に検証する。

## 優先する指摘

P1 は CI/CD で本格反映する前に対応する。P2 は関連修正に取り込むものと、その後に分けるものを以下の実施順で指定する。

### P1: DB 書き込み失敗時に人感観測を失う

根拠: [collector の受信処理](../cmd/hm-cisco-iot-orchestrator-collector/main.go) の `runWithReconnect`。`storeMotion` が失敗すると `continue` し、その観測を再試行用に保持しない。センサーから後続広告が来ることに依存し、短い状態遷移を失う可能性がある。バッテリーの集約への追加もこの分岐でスキップされる。

同じコールバックの最後の `flushPending` は、集約書き込みが0件でも `MarkSuccess` を呼ぶ。[共有ステータス処理](../internal/collectorstatus/status.go) はその呼び出しで `last_error` と連続失敗回数をクリアするため、一時的な保存失敗が直後に正常表示へ戻り得る。

対応: 受信・保存を分け、失敗した観測を順序を保って再試行する。接続の健全性と保存の健全性を区別し、未保存データがある間は保存障害をクリアしない。再起動をまたぐ保護には専用 volume の永続キューを使い、サイズ上限・残件数・最古待機時間・書き込み失敗を監視する。保存対象は人感・バッテリー観測と必要な識別情報に限定する。キュー満杯時に黙ってイベントを捨てない。

合格条件: DB の一時停止・復旧、保存応答の消失、collector 再起動を挟んでも、キューに記録済みの検出・解除を順序どおり保存し、重複イベントを作らない。未解決の保存障害を API の health が正常扱いしない。BLE/AP/MQTT で受信前に失われた広告の回復は、この仕組みでは保証できない。

### P1: MQTT の部分受信タイムアウトでフレーム境界を失う

根拠: [mqtt.go](../cmd/hm-cisco-iot-orchestrator-collector/mqtt.go) の `runMQTT` / `readMQTTPacket`。1秒の read deadline に達すると同じ接続で読み直すが、`io.ReadFull` が既に消費したヘッダーや本文の途中状態を保持しない。隔離テストで本文の途中にタイムアウトを入れ、次の読み取りが残りの本文を新しいヘッダーとして扱うことを確認した。

接続後の CONNACK/SUBACK 待機と書き込みにも期限・キャンセルの改善余地がある。現状は QoS 0、ランダム client ID、clean session であり、QoS 1 への設定変更だけでは対応できない。

対応: 最初に、途中まで読んだ場合の再接続と、ハンドシェイク・読み書き・キャンセルの期限を整える。無通信の待機と部分受信を区別する。保守されている MQTT クライアントへの置換は Sensor Connect 1.2.2 との接続・認証・再接続互換性を確認して判断する。QoS/セッション変更は broker 側の対応確認と別の検証を要する。

合格条件: ヘッダー・可変長・本文の各位置で分割・遅延・切断しても誤った観測を保存しない。応答が止まっても期限内に再接続・終了し、復旧後に購読を再開する。

### P1: Go と依存ライブラリーのセキュリティ更新

根拠: [Dockerfile](../Dockerfile) と [CI](../.github/workflows/ci.yaml) は Go 1.26.4、[go.mod](../go.mod) は `pgx/v5 v5.7.6`、`x/text v0.24.0`。今回の `govulncheck` で更新対象を確認した。

| 対象 | 最初の更新候補 | 根拠 |
| --- | --- | --- |
| Go ビルド環境 | 1.26.11。次の段階で1.27.4を評価 | 同系列のパッチ更新で変更範囲を抑える。[Go 公式リリース履歴](https://go.dev/doc/devel/release) |
| `github.com/jackc/pgx/v5` | v5.9.2以上 | [GO-2026-5004](https://pkg.go.dev/vuln/GO-2026-5004)。非デフォルトの simple protocol など成立条件があり、このアプリでの悪用を確認したものではない |
| `golang.org/x/text` | v0.41.0以上 | [GO-2026-5970](https://pkg.go.dev/vuln/GO-2026-5970) と [GO-2026-6629](https://pkg.go.dev/vuln/GO-2026-6629) の両方を対象にする |

これは2026-11-14の診断に対する最低候補であり、実装時に最新情報・推移依存・必要な Go バージョンを再確認する。必要に応じて1.27.4へ先に上げる。`go.mod` の `go 1.24` は最低言語バージョンで、現在のビルドコンパイラーとは別である。Docker・CI・開発手順のコンパイラーを揃え、最低サポート版も明記する。

合格条件: 全バイナリーのビルド、race 検出付きテスト、DB 結合、実機の回帰確認が成功し、更新後の `govulncheck` の未解決報告を個別に確認できること。

### P2: DB I/O が受信・集約を止める構造

根拠: [bthome.go](../cmd/hm-cisco-iot-orchestrator-collector/bthome.go) の `storeMotion` は集約と共用する mutex を保持したまま DB に問い合わせ、受信コールバックも同期的に待機する。遅い DB は受信や heartbeat を遅らせる。

対応: 純粋なデコード、受信観測のキュー、保存 worker を分離する。デバイス単位の順序を維持し、DB I/O を集約 mutex の外へ出す。操作単位の timeout を設ける。P1 の保存経路修正と同時に扱う。

### P2: 時刻・重複排除の境界条件を明確にする

根拠: 5秒のメモリーキャッシュと DB の最新観測時刻・状態で重複を抑制している。未来の送信元時刻を採用すると、後続の正常な観測が古いと判定される可能性がある。8bit packet ID は周回・再起動があるため、それだけを永続的な一意キーにできない。

対応: 送信元時刻・受信時刻・採用した観測時刻の役割を決め、許容 clock skew と fallback を実装する。複数 AP、遅延、再送、順序逆転、同時刻、ID 周回、センサー再起動、collector 再起動の fixture を追加する。初回状態と実際の検出回数を区別する既存仕様を維持する。SQL 関数の修正が必要なら新規 migration を使う。

### P2: DB 初期化とマイグレーションの二重管理

根拠: [schema.sql](../db/schema.sql) と migration の内容・チェックサム台帳を同期する必要があり、テストには migration 数を2件に固定した箇所がある。将来の追加で同期漏れが起きやすい。migration の同時起動を直列化する advisory lock もない。

対応: migration を正本に初期スキーマ・台帳を生成するか、新規 DB も migration で初期化する方式へ統一する。空 DB、既存 baseline、適用済み DB、同時起動を PostgreSQL 結合テストで検証する。**既に実機へ適用した `0002_shelly_motion.sql` は変更せず、追加修正は `0003` 以降にする。**

### P2: API・保存期間・グラフ定義の維持

根拠: [motion.go](../cmd/hm-api-server/motion.go) の履歴 API は最大5,000件で、続きの cursor がない。イベントの保存期間は未定義。数値の長期間 API と Grafana の SQL に別々の集約・直近データ結合の考慮が必要になる。

対応: `(observed_at, id)` によるページングを設計し、必要なインデックスを実行計画で確認する。イベント保存期間とバッテリーの長期集約方針を文書化する。期間の合意前に既存イベントの自動削除を追加しない。Grafana は今回追加した2パネルの SQL・設定を再現できる差分として管理し、既存のダッシュボード管理方針と整合させる。集計境界・直近の未集約区間・初回状態除外を結合テストする。

### P2: 共有化する小さな運用処理

各 collector に環境変数の解析・DB 設定・エラー処理の重複がある。正数が必要な interval の起動時検証を揃える。0や負数が `time.NewTicker` まで渡る経路を防ぐ。

[gatt_control.go](../cmd/hm-cisco-iot-orchestrator-collector/gatt_control.go) は通常 TLS 設定時に timeout のない `http.DefaultClient` を使い、ラボ向け設定時は呼び出しごとに transport を作成する。期限付きの共有 client に整理する。既存の証明書運用を変更する場合は接続互換性を別途確認する。

ローカル BLE collector はキャッシュ値をポーリング時刻で扱う経路を、実受信時刻で扱う設計へ見直す。BLE/Spaces collector の起動ログに DSN を直接出す箇所は、認証情報を含む URI を設定しても秘密を出さないようにする。これらは Cisco の新機能とは別の既存経路なので、変更・回帰確認を分ける。

BLE の共通デコーダーは `internal/ble` 等への移動候補。手書き protobuf の境界チェック・wire type・malformed 入力を fuzz で検証し、利用可能な正本の schema が確認できれば生成コードも評価する。プロトコルの異なる collector 全体を一度に共通フレームワークへ置換しない。

## 実施順と完了条件

| 段階 | 作業 | 完了条件 |
| --- | --- | --- |
| 1 | P1 の障害再現テスト、保存キュー・health・MQTT 修正、DB I/O 分離 | DB 障害・再起動・部分受信・再接続のテストが成功。検出・解除・電池を保存できる |
| 2 | Go・依存更新、DB migration/初期化の自動検証 | Docker/CI の版を統一。ビルド・vet・race・脆弱性検査・新旧 DB の結合検証を完了 |
| 3 | 関連する時刻・重複排除、API/Grafana 契約・再現性の整備 | 複数 AP で二重計数せず、初回状態を除く検出回数と電池の値・時刻が一致 |
| 4 | CI/CD を通さず開発イメージで再検証 | Cisco → DB → API → Grafana の実機確認。既存センサーの回帰なし。観測回数はユーザーと合わせる |
| 5 | 最終差分・検査結果・切り戻し手順を提示 | ユーザーの了承後に CI/CD で本格反映 |
| 後続 | 独立した既存 collector の整理、API ページング・保存期間、Rust 評価 | 各変更を独立してレビュー・検証できる |

CI には `gofmt` の差分検査、`go vet`、race 検出、`govulncheck`、PostgreSQL 結合テストを追加する計画とする。デコーダーは短時間の fuzz を PR で実行し、長時間実行は別ジョブとして評価する。ワークフローの実行は上記の了承段階に合わせる。

開発再配備では現行イメージ・Compose の差分・DB バックアップを保全する。追加 migration がある場合、旧アプリが追加済みスキーマで動くことを先に確認する。アプリの切り戻しと DB の復元は別手順とし、データを消す down migration を通常の切り戻し手段にしない。

## Rust 言語・コンパイラーの評価計画

2026-11-14時点の stable は **Rust 1.100.0（11月12日公開）**。[Rust 公式発表](https://blog.rust-lang.org/2026/11/12/Rust-1.100.0/)を確認した。導入する場合は `rust-toolchain.toml` と `Cargo.lock` で再現性を確保する。

1. Go の CPU・メモリー・受信から保存までの遅延を測定し、デコードが実際にボトルネックか確認する。
2. BTHome / protobuf の純粋なデコード部分を候補に、同じ正常・不正入力と実機 fixture で独立した Rust の試作を比較する。最初の比較は単体 CLI/ベンチとし、FFI や本番プロセスへの組み込みは後に判断する。
3. 結果の一致、panic/異常終了、割り当て量、処理量、起動・プロセス間通信の費用、イメージサイズ、ビルド・監視の負担を比較する。単体の速度向上に加え、全体の処理遅延や資源使用に実益があることを条件にする。
4. 実益が確認できた範囲だけ導入する。今回のイベント消失や通信境界の問題は保存・通信設計で解決し、Rust 評価の完了を Shelly 本格反映の必須条件にしない。

性能測定をしていない現時点では、Rust 化による高速化・省メモリー化の効果は未確定である。
